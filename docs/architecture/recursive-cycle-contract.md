# Recursive-cycle contract

PMCR-O may launch a child run to inspect or improve the infrastructure executing its parent. Recursion is an explicit, budgeted relationship—not permission for unlimited self-modification.

## Required identity and lineage

- Parent run ID and unique child run ID; organization/project/intent/correlation identity.
- Self-target identity and ordered ancestor target IDs to detect repeated targets and oscillation.
- Depth, maximum depth, remaining cycle budget, and deterministic stop conditions.
- Before-state snapshot reference, proposed diff/artifacts, rollback plan, and after-state evidence.
- Independent checker not responsible for the change; Trail Frames for proposal, authorization, action, verification, reflection, and outcome.

## Guard rules

1. Reject missing identities, parent/child ID reuse, exhausted budgets, invalid depth, and repeated self-targets.
2. Reject self-modification without a before-snapshot, rollback plan, and independent checker.
3. Require explicit approval for security/permission changes, secret-handling changes, external execution expansion, and production deployment.
4. Run tests and policy checks before accepting the child run. Failure, oscillation, or uncertain outcomes stop or escalate; do not self-certify success.
5. Record an append-only correction frame instead of rewriting prior evidence. The JSONL development adapter is single-process and is not a tamper-proof ledger.

## Child-run lifecycle

`PROPOSED → POLICY_CHECKED → APPROVED (when required) → SNAPSHOTTED → EXECUTED → INDEPENDENTLY_CHECKED → ACCEPTED | ROLLED_BACK | ESCALATED`

A learning proposal generated by a run is not automatically a validated lesson or policy. Reuse eligibility is granted only after the configured validation/approval process.
